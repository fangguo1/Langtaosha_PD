# Expanded Sparse Search Performance Diagnosis

Date: 2026-06-29
Branch: `feature-span-matcher-expanded-sparse-retrieval`
Scope: `search-use` API `expanded_sparse` query latency diagnosis

## Background

During `python3 app/dev/main_search_use.py api`, the `expanded_sparse` search path showed consistently high latency for repeated requests:

- `build_query_semantic_plan_ms`: about `5.6s` to `8.7s`
- `match_papers_by_expanded_sparse_plan_ms`: about `31.8s` to `32.0s`
- `total_elapsed_ms`: about `37.5s` to `40.7s`

Representative request:

```text
GET /api/search?query=kidney+fibrosis&search_type=expanded_sparse&top_k=5&hydrate=1&include_coverage=1&include_loose_coverage=0&source_list=langtaosha,biorxiv_history,biorxiv_daily
```

This report focuses on the root cause of the `match_papers_by_expanded_sparse_plan_ms` segment.

## Reproduction Setup

- Entry point: `app/dev/main_search_use.py`
- Search path: `PaperIndexer.expanded_sparse_search()`
- Query: `kidney fibrosis`
- Sources:
  - `langtaosha`
  - `biorxiv_history`
  - `biorxiv_daily`
- Database scale observed during diagnosis:
  - `papers`: `329399`
  - `paper_keywords`: `6950370`
  - `paper_sources`: `329861`

## Diagnostic Method

The diagnosis followed three steps:

1. Reproduce the latency with the same query path used by the API.
2. Inspect the semantic plan payload size before the DB query.
3. Capture and run `EXPLAIN ANALYZE` on the SQL generated by `MetadataDB.lookup_papers_by_expanded_sparse_groups()`.

## Key Findings

### 1. The Python-side payload is small

The query plan itself is not large for this case:

- `build_query_semantic_plan(...)` took about `8509.902 ms`
- `build_expanded_sparse_query_rows(plan)` produced only `7` rows
- The plan contained only `1` span group

Representative query rows:

```json
[
  {"group_id": 1, "span_id": "s1", "canonical_text": "Renal fibrosis", "span_scope": "parent", "child_span_id": null, "term_tier": "tier1", "match_mode": "exact", "term": "kidney fibrosis"},
  {"group_id": 1, "span_id": "s1", "canonical_text": "Renal fibrosis", "span_scope": "parent", "child_span_id": null, "term_tier": "tier1", "match_mode": "exact", "term": "renal fibrosis"},
  {"group_id": 1, "span_id": "s1", "canonical_text": "Renal fibrosis", "span_scope": "parent", "child_span_id": null, "term_tier": "tier2", "match_mode": "exact", "term": "fibrosis kidney"},
```

Conclusion: the `31s+` cost is not caused by a large semantic plan payload.

### 2. The hot path is SQL execution inside `lookup_papers_by_expanded_sparse_groups()`

The timing logged by:

- `src/docset_hub/indexing/paper_indexer.py`
- `src/docset_hub/indexing/expanded_sparse_retrieval.py`

maps directly to the SQL issued by:

- `src/docset_hub/storage/metadata_db.py`
- method: `lookup_papers_by_expanded_sparse_groups(...)`

Measured direct invocation:

- `match_papers_by_expanded_sparse_plan(...)`: `32161.427 ms`
- result count: `5`

Conclusion: the dominant cost is in the database query rather than Python post-processing.

### 3. `title_matches` and especially `abstract_matches` are the real bottlenecks

`EXPLAIN ANALYZE` showed the three UNION branches behave very differently:

- `title_matches`: about `5.4s`
- `abstract_matches`: about `26.6s`
- `keyword_matches`: about `37ms`

Conclusion: the expensive work is not in `paper_keywords`; it is in regex matching over `papers.canonical_title` and `papers.canonical_abstract`.

### 4. PostgreSQL is repeatedly sequentially scanning `papers`

The SQL in `lookup_papers_by_expanded_sparse_groups()` builds:

- `title_matches`
- `abstract_matches`
- `keyword_matches`

For `title_matches` and `abstract_matches`, the join condition applies regex matching directly on:

- `lower(COALESCE(p.canonical_title, ''))`
- `lower(COALESCE(p.canonical_abstract, ''))`

The execution plan showed repeated full-table scans:

```text
Seq Scan on public.papers ... rows=329399 loops=7
```

This happened in both the title and abstract branches because the query had `7` normalized term rows. In practice, the system is doing repeated regex evaluation across roughly `329k` papers, and the abstract branch is more expensive because the text is longer.

Conclusion: `match_papers_by_expanded_sparse_plan_ms` is dominated by repeated full-table regex scans on `papers`.

### 5. Current indexing helps `paper_keywords`, but not `papers` title/abstract matching

Existing schema support observed:

- `paper_keywords(lower(keyword))` index
- `paper_keywords` trigram GIN index

These make the `keyword_matches` branch fast.

There is no equivalent indexed search path in the current expanded sparse SQL for:

- `papers.canonical_title`
- `papers.canonical_abstract`

Conclusion: the keyword branch is already index-assisted, while title and abstract matching are not.

### 6. Duplicate normalized terms across tiers amplify the scan count

The current query-row builder keeps `term_tier` in the dedup key, so the same normalized text can appear more than once if it exists in both `tier1` and `tier2`.

In the reproduced case:

- `kidney fibrosis` appears in both `tier1` and `tier2`
- `renal fibrosis` appears in both `tier1` and `tier2`

This is not the main root cause, but it increases repeated work in the DB by causing extra scan iterations.

## Root Cause Summary

The main reason `match_papers_by_expanded_sparse_plan_ms` takes about `32s` is:

1. `lookup_papers_by_expanded_sparse_groups()` performs regex matching directly on `papers.canonical_title` and `papers.canonical_abstract`.
2. PostgreSQL cannot efficiently use an indexed access path for these predicates in the current SQL shape.
3. As a result, the query repeatedly sequentially scans the `papers` table for each normalized term row.
4. The `abstract_matches` branch dominates total execution time.

## Secondary Observation

There is a separate latency source earlier in the request:

- `build_query_semantic_plan_ms` was still around `5.6s` to `8.7s`

That is likely related to SpanMatcher / SciSpaCy / ontology initialization or per-request pipeline construction, but it is not the root cause of the `match_papers_by_expanded_sparse_plan_ms` measurement itself.

## Recommended Next Steps

### Priority A: make the bottleneck observable in API logs

Add sub-stage timing inside `lookup_papers_by_expanded_sparse_groups()` or around its branch logic so that API logs can separately report:

- title branch time
- abstract branch time
- keyword branch time
- SQL total time

### Priority B: remove avoidable repeated scans

Reduce repeated normalized terms before entering SQL, especially duplicates that differ only by `term_tier`.

### Priority C: redesign title/abstract matching to avoid repeated full-table regex scans

Candidate directions:

- Move title/abstract matching to an indexed search representation.
- Precompute a searchable sparse structure for title/abstract terms instead of regex scanning raw text.
- Rewrite the recall strategy so the expensive title/abstract branches use a narrower candidate pool before regex verification.
